# 完整终端恢复：方案评估

状态：评估完成，待确认是否引入一处依赖补丁（见第 5 节）。不改变 ADR-001。
证据可复现：`mise run probe-snapshot`、`mise run test`（`pulse-term` 的生成式测试）。

## 1. 结论

- **不需要为大部分隐藏状态修改 alacritty。** 之前失败的 8 组续流用例，除「非活动主屏」外已全部精确恢复，只用公开 API、一个透明的 Handler 镜像和一个转义序列边界扫描器。
- **唯一无法用公开 API 解决的是非活动网格**：备用屏激活时的主屏内容（以及备用屏自己的保存光标）。对应的补丁只是一个只读 getter（约 5 行），上游 master（0.26.1-dev）目前仍没有。
- 评估中发现了一个比恢复更常见的风险：**xterm.js 与 alacritty 在若干边缘序列上本身解析不同**（62 个序列中有 10 个在至少一种起始状态下不一致），实时显示可能与后端权威状态漂移。精确恢复可以把漂移纠正回来。
- 替代引擎 vt100 0.16.2 功能覆盖明显更窄；后端渲染方案代价过大。均不建议。

## 2. 验收口径

「完整恢复」= 原始终端处理 prefix 后生成恢复序列 R；新终端处理 R 后：

1. 结构指纹相同：所有可见单元格（字符、组合字符、宽字符标志、前/背景色、全部 SGR 与下划线样式/颜色、超链接 URI）、光标与保存光标（位置、画笔、G0–G3、待换行）、全部模式、滚动区、GL 字符集、制表位、调色板覆盖、光标样式；
2. 恢复本身不产生任何协议应答；
3. 两边再处理同一 suffix 后指纹仍相同；
4. 再发送 DSR、DECRQM（公共/私有）、OSC 4 查询，应答逐字节相同。

前端另设三个指标（xterm.js headless，生产解码路径与共享 Unicode 表）：M1 = xterm(R+suffix) 与 Rust(prefix+suffix) 一致；M2 = xterm(prefix+suffix) 与 Rust 一致（解析基线）；M3 = xterm(R+suffix) 与 xterm(prefix+suffix) 一致。

历史（scrollback）不在本次范围，单独按历史同步处理。

## 3. 状态清单与获取方式

| 状态 | 所在 | 公开？ | 获取 | 恢复 | 结果 |
|---|---|---|---|---|---|
| 可见单元格（字符/组合/宽字符/颜色/SGR/下划线色/超链接） | `Term::grid()` | 是 | 直接读取 | CUP + SGR + OSC 8 + 字符 | 精确 |
| 宽字符异常（孤立占位格、半截宽字符、末列无占位宽字符） | 同上 | 是 | 同上 | 配对后 DCH/ECH/ICH 定向重建 | 精确；末列连续两个异常为近似 |
| 复制用的制表符标记（HT 写入的 `\t`） | 同上 | 是 | 同上 | 在默认制表位下重放 HT | 精确 |
| 光标：位置、画笔、G0–G3、待换行 | `grid.cursor` | 是 | 直接读取 | 重写末格产生待换行；DECOM 区域外用 DECRC | 精确；右边界以外的待换行标志（经 CBT/LF 保留）VT 无法表达→近似 |
| 保存光标（DECSC） | `grid.saved_cursor` | 是 | 直接读取 | 主屏：进入 1049 时的自动保存；备用屏：DECSC | 精确 |
| 模式（DECCKM、DECAWM、DECTCEM、DECOM、IRM、LNM、鼠标、焦点、粘贴、键盘 DECKPAM 等） | `Term::mode()` | 是 | 直接读取 | DECSET/SM | 精确 |
| 调色板覆盖（OSC 4/10/11/12） | `Term::colors()` | 是 | 直接读取 | OSC 设置 | 精确 |
| 光标样式（DECSCUSR） | `Term::cursor_style()` | 是 | 直接读取 | DECSCUSR | 精确（HollowBlock/Hidden 无 VT 对应） |
| 滚动区、GL 字符集（SO/SI）、制表位 | `Term` 私有字段 | 否 | **透明 Handler 镜像** | DECSTBM/SO/HTS | 精确 |
| REP 前导字符 | vte `Processor` 私有 | 否 | 透明 Handler 镜像 | 主屏：在临时备用屏打印一次；备用屏：幂等重写一个同字符单元格 | 主屏精确；备用屏尽力；「从未打印」状态不可复原 |
| 未完成的转义序列与 UTF-8 尾部 | vte 私有 / 已有 `utf8_tail` | 否 | 边界扫描器（以 vte 为预言机做差分测试） | 追加原始尾部字节（≤ 64 KiB） | 精确；超长则延后恢复 |
| 同步更新（DEC 2026）缓冲 | vte 私有 | 部分（`sync_timeout`/`sync_bytes_count`） | 查询是否进行中 | 不恢复，返回 `SyncPending`，结束或超时后重试 | 延后 |
| **非活动网格**（备用屏时的主屏内容；备用屏的保存光标） | `Term::inactive_grid` 私有 | 否 | 只能经 `swap_alt()`，而它会覆盖保存光标并清空备用屏（破坏性） | — | **缺口** |
| 标题栈、kitty 键盘栈 | 私有 | 否 | 未处理 | — | 不影响显示；kitty 协议默认关闭 |

透明 Handler 镜像：解析器的每一个 `Handler` 调用都原样转发给 `Term`，只额外记录上述私有状态；更新规则抄自 alacritty_terminal 0.26.0（已精确锁定），包括 DECCOLM、RIS、resize 的间接修改。升级依赖时必须重新核对，生成式测试会发现漂移。

## 4. 验证结果

**透明性**：生成式测试证明经镜像 Handler 的终端与直接使用 `Term` 的终端逐单元格、光标、保存光标、模式完全一致。边界扫描器以 vte 为预言机做生成式差分测试，且重放尾部可复现解析状态。

**Rust 往返（3 万组随机流，80 种序列量子，24×6）**：

| 类别 | 数量 | 说明 |
|---|---|---|
| 精确（含续流 + 查询应答） | 15 497 | 无一失败 |
| 同步更新进行中，延后 | 8 473 | 随机生成的 BSU 多未结束；真实程序 150 ms 内结束 |
| 备用屏激活（主屏缺失） | 4 583 | 其中 1 198 组对可见备用屏与不离开备用屏的续流做了精确校验，全部通过 |
| 再次进入备用屏（暴露其保存光标） | 508 | 非活动网格缺口 |
| 近似 | 196 | 右边界外待换行、DECOM 区域外光标且保存光标不同、待换行重写与 REP 字符冲突等，均在恢复结果中显式标注 |

**命名用例（32×8）**：普通文本、待换行、宽字符待换行、保存光标（含画笔与字符集）、滚动区、DECOM、插入模式、字符集指定、SO/G1、无文字的画笔、制表位、调色板覆盖、输入模式、超链接画笔、未完成 CSI/OSC/UTF-8 共 16 组在 Rust 与 xterm 两侧均通过；非活动主屏为缺口；同步更新为延后。此前的 8 组失败用例已全部覆盖。

**xterm.js 侧（含命名用例 + 600 组种子随机流，32×8）**：严格用例 429 组，M1 295、M2 232、M3 339；**凡 xterm 对原始流的解析与 Rust 一致（M2），恢复后也一致（232/232）**。M1 高于 M2：恢复把两个解析器理解不同的历史压平为双方一致的简单序列，因此可用于纠正实时漂移。

**双解析器分歧矩阵（6 种起始状态 × 62 个序列）**：10 个序列至少在一种状态下不一致，且多为 alacritty 偏离 xterm 参考行为：

- 待换行时 HT：alacritty 换行，xterm.js 停在末列；
- 重置 DECOM（`?6l`）：xterm.js 光标归位，alacritty 不归位；
- 不在备用屏时的 `?1049l`：xterm.js 仍执行 DECRC，alacritty 忽略；
- IL/DL：xterm.js 光标回到行首，alacritty 不动；
- 光标位于宽字符右半时的 EL/DCH/ICH/ECH：xterm.js 清除整个宽字符，alacritty 留下半截宽字符；
- DECOM 下恢复默认保存光标：两者位置不同。

影响：这些场景下用户看到的画面与后端状态不同，而 DSR 等查询由后端应答。此外 xterm.js 把超链接单元格报告为虚线下划线（渲染策略，非状态差异）。

**规模**：120×40 全屏每格不同颜色时恢复序列 163 641 字节，生成约 1 ms（release）；纯文本 62 105 字节。序列化器尚未优化（每格 CUP + 完整 SGR），合并连续单元格与 SGR 差分后可显著缩小。

## 5. 方案对比

### A0：无补丁（已实现并验证）

镜像 + 边界扫描 + 公开 API 序列化。覆盖除非活动网格外的全部状态。

缺口的用户影响：在 vim、less、htop 等全屏程序运行时刷新视图、移动标签或重新关联，程序退出后主屏可见区域为空白（后端仍完整，只是显示丢失）。

可选缓解 A0+：在进入 1049 前捕获主屏可见行与光标（每次约行数×列数×24 B，120×40 约 115 KB）。但备用屏期间调整窗口大小时，alacritty 会带历史重排主屏，捕获副本无法精确复现，只能标为近似；全量克隆含历史又会在每次启动 vim 时复制数十 MB。

### A1：A0 + 一个只读 getter（建议）

给 alacritty_terminal 增加 `pub fn inactive_grid(&self) -> &Grid<Cell>`（约 5 行，不改变任何解析行为）。有了它，备用屏激活时可先写主屏、再进入 1049 写备用屏（主屏在备用屏期间的光标与保存光标相同，进入 1049 的自动保存恰好复现）。

- 维护：精确锁定版本的 `[patch]`，保留许可证与 diff；同时向上游提 PR（只读访问器，接受可能性较高），合入后去掉补丁。
- 与此前撤销的 GTK 宏补丁无关；不影响审计规则。
- 剩余已知项：「从未打印」的 REP 状态、第 4 节列出的近似项、同步更新延后。

### B：换用 vt100 0.16.2

已核对其分发代码：不支持 G0–G3 字符集与 SO/SI、HTS/TBC、IRM/LNM、DECAWM、REP、OSC 4/8/10–12、DECSCUSR、DEC 2026，也不应答 DA/DSR/DECRQM；`state_formatted()` 只序列化可见内容和输入模式。要达到现有兼容性需要大量补功能（等同长期 fork），优于 A 的地方只有「不用镜像」。不建议。

### C：后端渲染（Rust 是唯一解析器）

前端只绘制格子，根本消除双解析器分歧与恢复问题；代价是自研渲染、输入法、选择、无障碍、字体与性能，xterm.js 也没有稳定的格子导入接口。当前证据（分歧只在边缘序列、可通过精确恢复纠正）不支持这样大的变更。

## 6. 建议与后续

1. 采用 A0（已完成）作为恢复实现；**是否引入 A1 的一处 getter 补丁等待确认**。不引入时，备用屏期间的重新关联按缺口处理（可加 A0+ 缓解），并向上游提 PR。
2. 增加「重新同步」策略：在关联/视图重建、尺寸变化、空闲、及检测到上述分歧序列后用恢复序列重置显示，纠正双解析器漂移。
3. 生产接入前仍需：actor 驱动同步更新超时（否则 BSU 未结束时恢复会一直延后）、序列化器体积优化、历史同步、真实 vim/htop/tmux 录制流回归、与前端额度协议整合。
4. 保留不做的绕过：不把视口相同当作恢复通过；不保留所有隐藏 xterm 实例；不无界保存原始输出重放。
